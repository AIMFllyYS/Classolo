模式 A · 静态导出 + 特权自定义协议 当前推荐方案

定位：把 Next.js 当成静态站点生成器，Electron 只负责窗口、权限、通知、本地文件与自动更新。开发期仍 next dev（4070）；打 exe 时吃 out/。

核心能力（来自 Next.js / Electron 官网）

  • Next.js：output: 'export' 在 next build 后生成 out/ HTML/CSS/JS，可部署到「任何能托管静态资源的环境」。
  • Server Components 在构建期运行；Client Components 构建期预渲染后按 SPA 在客户端导航。
  • Electron 安全清单第 18 条：避免 file://，改用自定义协议。协议文档要求 registerSchemesAsPrivileged 把 scheme 注册为 standard + secure，否则相对 URL / IndexedDB 等会按非标准 scheme 失败。
1. 最近发布 / 版本模式本身无独立 npm 包。依赖 Electron 44.0.0（2026-08-25）与项目已用的 Next 16 静态导出。
2. 维护方 / bus factorNext.js（Vercel）+ Electron 官方 API。无第三方脚手架单点。
3. 构建复杂度低–中：新增 electron/ main+preload、一条协议 handler、builder 配置。不改 App Router 目录。
4. install 脚本无额外脚手架。Electron 无 postinstall；构建时 electron-builder 再拉 NSIS 工具（构建期下载，非 install 脚本）。
5. 许可证Electron MIT；Next.js 以项目依赖为准（本次未单独展开 Next 许可证页）。
6. Next 16 App Router 证据Next 官方 Static Exports：不支持 Server Actions、依赖 Request 的 Route Handlers、Cookies、Rewrites/Redirects/Headers/Proxy、ISR、默认 next/image loader、Intercepting Routes、无 generateStaticParams 的动态路由。Route Handler 仅支持静态 GET，且须 export const dynamic = 'force-static'。
7. 文档质量Next 静态导出页 + Electron protocol / security 均为官方一等文档。
8. 体积 / 更新不内嵌 Next 服务器，体积接近 Electron 基线 zip（150.2 MB）+ 静态资源。更新交给打包器，本模式不自带更新。

关键配置示例（协议片段取自 Electron protocol 文档；Next 配置与 Classolo 仓库现状一致）：

// next.config.ts（仓库已有）
const nextConfig = {
  output: 'export',
  images: { unoptimized: true },
  trailingSlash: true,
}

// electron/main.ts — 自定义协议（官方示例结构）
protocol.registerSchemesAsPrivileged([{
  scheme: 'app',
  privileges: { standard: true, secure: true, supportFetchAPI: true },
}])
app.whenReady().then(() => {
  protocol.handle('app', (req) => {
    const { pathname } = new URL(req.url)
    const pathToServe = path.resolve(outDir, pathname === '/' ? 'index.html' : pathname)
    // 必须做路径逃逸检查，见 Electron protocol.handle 文档
    return net.fetch(pathToFileURL(pathToServe).toString())
  })
  win.loadURL('app://bundle/')
})

适合 Classolo 吗？适合，作为桌面集成的默认路径。 麦克风、通知、PGlite 文件、后台任务都应放在 main；renderer 只跑导出后的 UI。现有 src/app/api/ping/route.ts 返回动态 Date.now()，与静态导出规则冲突，桌面端应改为 IPC，而不是指望 Route Handler。

模式 B · 打包内嵌 Node 服务跑 next start / standalone

定位：Electron 启动一个 Next 生产服务器（官方 output: 'standalone' 产出的 server.js），窗口再 loadURL('http://127.0.0.1:…')。

核心能力（Next.js output 文档）

  • output: 'standalone' 把追踪到的生产文件（含部分 node_modules）拷到 .next/standalone，可用 node server.js 代替 next start。
  • public 与 .next/static 默认不在 standalone 内，需手动拷贝后由 server.js 提供。
  • 可用 PORT / HOSTNAME 环境变量指定监听地址。
1. 最近发布 / 版本同样依附 Electron 44 + Next 16。standalone 是 Next 配置能力，不是独立包。
2. 维护方Next 官方。Electron 侧要自写 spawn/生命周期，无单一维护脚手架。
3. 构建复杂度高：两套 output 互斥（Classolo 已是 export，EdgeOne 也吃静态）；要管端口、退出杀进程、asar 解包、把 WASM/原生模块打进 standalone trace。
4. install 脚本无额外。若拷入原生模块，仍要走 @electron/rebuild。
5. 许可证同 Next / Electron（MIT for Electron）。
6. Next 16 兼容证据此模式保留完整 App Router 运行时：Route Handlers、Server Actions、Cookies 等在「有 Node 服务器」时可用。官方静态导出页明确这些能力需要 Node 服务器。本次未找到 Next 官方「请在 Electron 内跑 standalone」指南，社区实践有、官方集成文档未核实。
7. 文档质量standalone 文档针对 Docker/CDN 部署，不是桌面壳。
8. 体积 / 更新在 Electron ~150 MB 之上再打入 Next server + traced node_modules。增量体积未实测，不编造数字。自动更新仍取决于打包器。

关键配置示例（官方 standalone）：

// next.config.ts — 与现有 output:'export' 互斥
export default { output: 'standalone' }

// 构建后（官方文档命令，Linux/mac；Windows 用 Copy-Item）
// cp -r public .next/standalone/ && cp -r .next/static .next/standalone/.next/
// node .next/standalone/server.js   // PORT=4070 HOSTNAME=127.0.0.1

适合 Classolo 吗？不适合作为 P0 默认。 会拆掉已锁定的静态导出 / EdgeOne 路径，换来 Classolo 桌面并不需要的 Server Actions。本地库、麦克风都不依赖 Next 服务器。

模式 C · Nextron 脚手架

定位：nextron / create-nextron-app 把 Next renderer + Electron main + webpack 主进程 + electron-builder 绑成一套 CLI。

核心能力（Nextron README，npm 10.3.0）

  • 官方版本表：Next v16.x ↔ Nextron v10.x。
  • 生产构建强制 output: 'export'，trailingSlash: true，images.unoptimized；生产 distDir 改到 ../app 给 electron-builder 吃。
  • 维护者原文（Discussion #254，2022，至抓取日 README 未改口）：生产只能处理静态文件，API routes 不可用。
  • 官方示例目录仍是 renderer/pages/（Pages Router）。README 未展示 App Router 模板。
1. 最近发布 / 版本nextron 10.3.0，npm time 2026-08-21。create-nextron-app 5.4.0，同日 2026-08-21。
2. 维护方 / bus factor仓库属主为个人账号 saltyshiomix（Yoshihide Shiono）。README 列出 8 名 maintainers，并链到 Discussion #244「Looking for maintainers」。GitHub：4,429 star、113 open issues、pushed 2026-08-21。应视为个人项目 + 志愿者，不是 Electron 官方。
3. 构建复杂度对绿场低；对 Classolo 高：强制 main/+renderer/ 分裂、distDir: '../app'、主进程 webpack（nextron.config.ts）、与现有 src/app 和 EdgeOne out/ 冲突。
4. install 脚本nextron 自身是 CLI（chalk/commander/webpack…）。Electron 二进制仍走 electron 包。未在 nextron latest README 中看到原生模块 postinstall。
5. 许可证MIT（npm 与 GitHub license 一致）。
6. Next 16 兼容证据官方 README 表格写明 v10.x 对应 Next v16.x，且 next.config 必须 export。因此 App Router 能用的子集 = Next 静态导出子集；Server Actions / 动态 Route Handlers 仍不行。Issue #311 为 Next 13 app dir 历史讨论，不能当作 2026 官方 App Router 模板。
7. 文档质量单页 README + examples；深度不如 Electron / Next 官网。
8. 自动更新 / 体积底层就是 electron-builder（electron-builder.yml）。更新能力等于 builder，不额外减小 Electron 基线体积。npm 周下载本次页面展示约 3.5k 量级（registry 摘要）。

关键配置示例（官方 README renderer/next.config.ts）：

const config: NextConfig = {
  output: 'export',
  distDir: process.env.NODE_ENV === 'production' ? '../app' : '.next',
  trailingSlash: true,
  images: { unoptimized: true },
}
export default config

适合 Classolo 吗？不建议引入。 它把 Classolo 已经自己做的事（export + trailingSlash + unoptimized）再包一层 webpack/目录约定，bus factor 偏个人，还与 EdgeOne 的 out/ 打架。可当参考实现，不要当运行时依赖。

打包器 · electron-builder + electron-updater 当前推荐方案

定位：官方自述「完整的 macOS/Windows/Linux 打包方案，开箱即用自动更新」。Windows 默认目标 NSIS。

核心能力（electron.build）

  • Windows：nsis（安装器）、nsis-web、portable、AppX、MSI、Squirrel.Windows。NSIS 是默认 Windows 目标。
  • 自动更新：electron-updater；Windows 可更新目标是 NSIS（文档写明 Squirrel.Windows 不被 electron-updater 支持）。
  • 发布渠道：GitHub Releases、S3、Spaces、Cloudflare R2、Keygen、generic HTTP。
  • NSIS 文档要求 app.setAppUserModelId(appId)，否则 Windows 通知图标/AUMID 异常。
  • Electron 44 起 ia32 安装器需要 electronVersion <= 43——Classolo 用 44 则只打 x64。
1. 最近发布 / 版本 npm latest = 26.15.3（2026-06-09）。
npm dist-tag v26 = 26.15.7（2026-07-18）——比 latest 新。
npm next = 27.0.0-alpha.7（2026-08-17）。
electron-updater latest = 6.8.9（2026-06-05）；next = 7.0.0-alpha.6（2026-08-17）。
2. 维护方 / bus factorGitHub org electron-userland/electron-builder（14,655 star，2026-08-30 仍有 push）。npm maintainers：stefanjudis、develar、onegoldfishh；contributors 写明 Stefan Judis、Mike Maietta。社区项目但活跃，非 Electron 核心仓。
3. 构建复杂度中：一份 electron-builder.yml（或 package.json build）。NSIS 选项多，默认 one-click 即可起步。
4. install 脚本latest 包 JSON 无 scripts.postinstall。提供 bin electron-builder 与 install-app-deps（原生依赖按 Electron ABI 重编）。NSIS 工具在打包时下载，不是 npm install 时编译 C++。
5. 许可证MIT。
6. Next 16 兼容打包器不解析 App Router。只要把 out/（或 Nextron 的 app/）列入 files 即可。Nextron 官方生产路径就是 builder，可作旁证。
7. 文档质量electron.build 文档完整（NSIS、auto-update、publish）。v27 有独立 breaking changes 页。
8. 自动更新成熟度高：两行 autoUpdater.checkForUpdatesAndNotify()；产出 latest.yml。已知坑：Windows 关机过程中 on-quit 安装可能把应用装坏（issue #7807）；缓解在 updater ≥7 / builder v27 的 autoInstallEvent = "onNextLaunch"，但 6.8.9 latest 仍是 v6 线。v27 起 disableWebInstaller 默认 true。

关键配置示例：

# electron-builder.yml
appId: com.1037solo.classolo
productName: Classolo
directories:
  output: dist
  buildResources: electron/resources
files:
  - package.json
  - electron/**
  - out/**
win:
  target: nsis
nsis:
  oneClick: false
  allowToChangeInstallationDirectory: true
publish:
  provider: generic
  url: https://your-update-host/classolo/win/  # 宝塔静态目录即可

适合 Classolo 吗？适合。 不上应用商店、要 NSIS exe、可能要自动更新、可能自建 HTTP 分发——这正是 electron-updater + generic/GitHub 的场景。安装时请显式钉 electron-builder@26.15.7（或 dist-tag v26），不要盲信 npm latest=26.15.3。v27 仍是 alpha，P0 不跟。

打包器 · Electron Forge

定位：Electron 官方「all-in-one」打包/签名/发布工具链（Plugin / Maker / Publisher）。

核心能力（electronforge.io）

  • npx create-electron-app；一等模板是 webpack / vite，不是 Next.js。
  • 官方 Windows Maker：Squirrel.Windows（Setup.exe + nupkg + RELEASES）与 WiX MSI。文档推荐 Squirrel 而不是 MSI。
  • 官方自动更新教程：Forge 用 ZIP Maker（macOS）与 Squirrel.Windows remoteReleases；或 update.electronjs.org（要求公开 GitHub 仓库 + GitHub Releases；macOS 还要签名）。
  • pnpm：官方警告 Forge 解析 node_modules 很朴素，必须 node-linker=hoisted。
  • 原生模块：官方 Native Modules 文档写明 Forge 在 dev 与 make 时自动跑 @electron/rebuild。
1. 最近发布 / 版本@electron-forge/cli latest 7.11.2（2026-05-20）。dist-tag alpha = 8.0.0-alpha.10（2026-07-02）。GitHub electron/forge pushed 2026-08-28，仓还活着，但 npm latest 已 102 天。
2. 维护方 / bus factorElectron 官方 org，wg-ecosystem。7,134 star。npm maintainers 含 marshallofsound、erickzhao 等。bus factor 优于 Nextron / electron-vite。
3. 构建复杂度中–高：forge.config.* + Maker/Publisher/Plugin 组合。与现有 Next 静态导出要自己写 hook 去 next build。

5. 许可证MIT。
6. Next 16 兼容官方模板无 Next。兼容性 = 你自己把 export 产物塞进 Forge packagerConfig。无官方 Next 16 指南（本次未核实到）。
7. 文档质量electronforge.io 结构清晰，Maker/Publisher 分页。
8. 自动更新 / NSIS官方路径是 Squirrel.Windows + Electron 内置 autoUpdater / update.electronjs.org，不是 electron-updater+NSIS。NSIS 需 @electron-addons/electron-forge-maker-nsis 或 electron-builder 自己的 forge maker——第三方，成熟度低于 builder 一等 NSIS。electron-updater 文档明确不支持 Squirrel.Windows。

// forge.config.js
module.exports = {
  makers: [
    { name: '@electron-forge/maker-squirrel', config: { /* remoteReleases 可选 */ } },

适合 Classolo 吗？可作为备选，不是第一选择。 官方地位高，但 Windows 默认安装器/更新协议与「NSIS exe + 自建 HTTP 更新」不一致；pnpm 还要 hoist。若未来放弃 NSIS、改走 Squirrel 静默安装，再评估。

旁路 · electron-vite

定位：基于 Vite 的 Electron 构建工具（main / preload / renderer 一份配置）。官网强调「为 Electron 的双环境打包」，脚手架是 Vue/React/Vanilla，不是 Next.js。

1. 最近发布 / 版本npm latest 5.0.0（2025-12-07）。6.0.0-beta.1 于 2026-04-12。距抓取日 latest 已 266 天。
2. 维护方 / bus factor作者 Alex Wei（alex8088），npm 单一 maintainer alex.wei。个人项目。
3. 构建复杂度对 Vite 应用低（electron.vite.config.js）。对 Next App Router 等于换框架。
4. install 脚本未在 latest 包 JSON 中见到 postinstall。peer：Vite 5/6/7。
5. 许可证MIT。
6. Next 16 兼容证据官方 Getting Started 无 Next 模板。Vite renderer ≠ Next App Router。评为不兼容（换栈）。
7. 文档质量electron-vite.org 完整，但对象是 Vite 应用。
8. 更新 / 体积脚手架可勾选 updater 插件；体积仍受 Electron 基线约束。与 Next 选型正交。

关键配置示例（官网最简）：

// electron.vite.config.js
export default {
  main: {},
  preload: {},
  renderer: {},
}

适合 Classolo 吗？不适合。 Classolo 已押 Next 16 App Router + EdgeOne 静态导出。electron-vite 解决的是「不用 Next 的 Electron 应用」。

横切能力：麦克风 / WASM / 原生模块 / 通知 / 后台

这些不随脚手架改变；必须在 Electron main 显式处理。下列均来自本次抓取的官方文档。

麦克风 getUserMedia（Windows） Renderer 调 navigator.mediaDevices.getUserMedia 时，session 权限字符串为 media。必须同时实现 ses.setPermissionRequestHandler 与 ses.setPermissionCheckHandler（官方 session 文档：只实现其中一个不完整）。 systemPreferences.getMediaAccessStatus('microphone') 在 Windows/macOS 可用；Windows 10 用全局隐私开关控制所有 Win32 应用的麦/摄像头，旧版 Windows 对该 API 恒为 granted。 askForMediaAccess 仅 macOS。Windows 被拒后只能引导用户去系统设置（社区常用 ms-settings:privacy-microphone，非 Electron 官方 API）。
系统通知 Main：new Notification().show()；Renderer：Web Notification API。Windows 需要 Start Menu 快捷方式 + AppUserModelID；electron-builder NSIS 文档要求尽早 app.setAppUserModelId(appId)。开发期未安装时通知可能静默失败。
「请勿关机」/ 后台任务 powerSaveBlocker.start('prevent-app-suspension' | 'prevent-display-sleep') 只能阻止休眠/息屏，不能阻止用户关机。关机提醒应发 Notification。本次未核实到 Electron 有拦截 Windows 关机的官方 API。
PGlite WASM 官方：浏览器用 idb://（推荐）或 Worker 内 opfs-ahp://；Node/Bun 用目录路径 / NodeFS。Electron renderer ≈ Chrome（IndexedDB 可用）；Electron main ≈ Node（应把数据目录指到 app.getPath('userData')）。 自定义协议须 standard + secure + supportFetchAPI，否则 IndexedDB 在非标准 scheme 上默认关闭。 若将来用 SharedArrayBuffer / 某些 Worker VFS，需在 protocol.handle 响应里自行加 COOP/COEP——PGlite 文件系统文档未写 Electron 专页，COOP 头方案标「需实测」。 PGlite 是 WASM/TS，不需要 @electron/rebuild。
better-sqlite3 等原生模块 Electron ABI ≠ 系统 Node。官方：用 @electron/rebuild 4.2.0（npm 2026-07-07，MIT）；Forge 会自动调。Windows 还要求 win_delay_load_hook: true。每次升级 Electron 通常要重编。 electron-builder 用 install-app-deps 做同类事。Classolo 架构已选 PGlite，P0 不必引入 better-sqlite3。
file:// 已知坑 相对路径解析失败、web storage 关闭、无法用 HTTP 头送 CSP、XSS 可读任意本地文件。Next 的 /_next/static 与 trailingSlash 路由在 file:// 下极易 404。官方结论：自定义协议。

决策历史

  1. 2026-08-30 · AI 初步推荐：静态导出 + 特权自定义协议 + electron-builder（NSIS）+ electron-updater。 理由：与已落地的 output:'export' / EdgeOne / 本地优先一致；Electron 官方禁止生产依赖 file://；builder 对 NSIS 与非商店自动更新是一等能力。Nextron 只是同一模式的个人脚手架；内嵌 next start 与静态导出互斥且无桌面收益。
